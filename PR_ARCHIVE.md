## #2 — M2: Hybrid Retrieval (spec.md §9)

*MERGED*

## What

Implements M2 — Hybrid Retrieval (`ROADMAP.md`, spec.md §9): `query -> seed nodes`.

**`packages/retrieval`** (new):
- **Lexical leg**: `pg_trgm` trigram similarity over `nodes.name`/`nodes.path` (not `tsvector` — spec.md §9 is explicit about why: it degrades gracefully on partial/typo'd identifiers).
- **Vector leg**: cosine similarity over `nodes.embedding`, behind an injected `EmbeddingProvider` interface — the package has no hard dependency on a specific embedding API. Tests use a deterministic hashing-trick fake embedder (`createFakeEmbedder`).
- **Merge + de-dupe**: a node hit by both legs is tagged `hybrid_match` and scored by its stronger leg; lexical-only is `lexical_match`, vector-only is `semantic_match`.
- **Seed expansion** (spec.md §9, closing v0.1 review gap #7 — "a node can be a poor initial search result but extremely relevant once reached"): 1-hop structural neighbors of the top-3 merged hits, plus the highest-weight semantic neighbors of any matched `concept`/`invariant` node.

**`packages/graph-store`** additions (the read primitives retrieval needs):
- `searchNodesByTrigram`, `searchNodesByEmbedding`, `upsertNodeEmbedding`, `getNeighborEdgesByRelation`.
- Both search functions take an optional `repoId` scope, mirroring the existing `getNodesByPath` pattern — without it, hybrid search would bleed across repos sharing one Postgres instance (relevant for eval/test isolation, and for any real multi-repo deployment).

**`packages/core`** additions:
- `STRUCTURAL_RELATIONS` / `SEMANTIC_RELATIONS` runtime arrays, mirroring the existing `EVIDENCE_HIERARCHY` pattern, so retrieval can filter edges by relation-type set without hand-duplicating the union types.

**`eval/retrieval`** (new — first slice of spec.md §19's eval plan, per the ROADMAP note to keep it here so M7 extends rather than restarts):
- A small PaymentService-domain fixture built through the **real M1 extractor** (`extractProject`/`persistExtraction`), plus one synthetic `invariant` node/edge — concept/invariant nodes don't exist until M3's promotion pipeline, but §9's semantic-neighbor-expansion path needs one to be exercised now, at M2.
- **23 hand-labeled `(query -> expected node)` pairs** (`cases.ts`) covering: direct lexical/vector hits, 1-hop structural-neighbor expansion, and semantic-neighbor expansion of a matched invariant — satisfying the ROADMAP acceptance criterion ("hits the expected node in the seed set, including via 1-hop expansion, not just direct hits").

## #3 — M3: Semantic Memory Pipeline (spec.md §6-§7, §13)

*MERGED*

## What

Implements M3 — Semantic Memory Pipeline (`ROADMAP.md`, spec.md §6-§7, §13): the observation → hypothesis → candidate → durable promotion table, plus conflict resolution.

**`packages/semantic`** (new):
- `confidence.ts` — `resolveConfidence()` combines a triple's accumulated provenance into one confidence value via an evidence-hierarchy-weighted average (exponential tier weighting, so a trusted source dominates rather than getting averaged down by a less-trusted one — spec.md §13's "Fact A wins" example). Flags `disputed` when the top-ranked sourceType present has ≥2 records disagreeing beyond a threshold — the only case the hierarchy genuinely can't arbitrate, since every `ProvenanceSourceType` has a distinct rank.
- `promotion.ts` — `computePromotion()` is a priority ladder over spec.md §7's four stages. Both of the "hypothesis" row's conditions (confidence < 0.5, fewer than 2 distinct sourceTypes) gate independently — neither alone is sufficient to reach "candidate" (see the self-review section below for why this needed tightening).
- `edge.ts` — `recordObservation()` merges a new provenance record into an existing edge and persists it through `graph-store`, inside a `pg_advisory_xact_lock`-guarded transaction so concurrent observations on the same triple can't lose each other's provenance in a read-modify-write race.

**`graph-store` fixes** (needed to get real tests passing against real Postgres, not scope creep for its own sake):
- `upsertEdgeByTriple` never persisted `last_verified_at` at all, despite the column and `Edge.lastVerifiedAt` already existing — M3 is the first caller that actually needs it (durable-via-verification).
- `listEventsSince`/`appendEvent` compared `bigserial` ids as strings (node-postgres returns `bigint` columns as strings), so `id > $1` did lexicographic, not numeric, comparison client-side — silently broken once ids crossed a digit boundary (I hit this for real: ids were at 9→10 in the dev DB). Now converted explicitly.
- `getEdgeByTriple`/`upsertEdgeByTriple` accept an optional `Queryable` (`Pool | PoolClient`) so a caller running its own transaction can execute them on its held connection instead of borrowing a second one from the pool — avoids a deadlock under concurrency (see self-review below).

**`core`**: `EVIDENCE_HIERARCHY` only covered 5 of 7 `ProvenanceSourceType` values. Extended to all 7 — `pull_request` ranked above `git_commit` (a reviewed diff carries more context than a bare commit message), `agent_experience` above `llm_inference` (grounded in an actual observed result vs. pure speculation). See the code comment for full rationale. This fills a gap the array left relative to its own type, it doesn't override anything spec.md decided.

## Self-review (code-review skill, high effort)

Found and fixed 2 issues:
1. **Confirmed lost-update race** in `recordObservation`: two concurrent calls on the same triple could both read the same snapshot and each overwrite with a single-provenance array, silently dropping the other's observation. The reviewer verified this empirically against real Postgres before I fixed it. Fixed with an advisory-lock-guarded transaction; added a regression test that fires 7 concurrent `recordObservation` calls on a brand-new triple and asserts all 7 provenance entries survive.
2. **Promotion-ladder gap**: my original implementation gated "hypothesis" purely on sourceType diversity, which meant 2 distinct-sourceType observations with *low* confidence (e.g. 0.1 each) would reach "candidate" purely on diversity, contradicting spec.md's literal "hypothesis: confidence < 0.5" condition. Fixed by requiring confidence ≥ 0.5 *in addition to* diversity for candidacy; added a test for the low-confidence-but-diverse case.

Fixing #1 surfaced the `Queryable` deadlock risk (running the merge on the shared pool while N concurrent callers each hold a connection blocked on the lock can exhaust the pool) and the `last_verified_at` persistence bug (needed to make the "durable" test assertions meaningful) — both fixed as part of the same pass, with tests re-run after each fix.

## Manual sanity check

Ran a 3-step realistic scenario through `recordObservation` against real Postgres — not copied from the unit/eval fixtures — and read the actual output:

1. An agent's initial code-reading hunch ("`InventoryService` looks like it depends on `WarehouseSyncJob`"), `llm_inference @ 0.55` → **observation**, confidence 0.550.
2. A corroborating git commit found later, `git_commit @ 0.7` → **candidate**, confidence **0.670**.
3. A test that verifies it, `test @ 0.95`, `verified: true` → **durable**, confidence **0.912**.

Hand-checked the weighted-average arithmetic at each step against the hierarchy weights (git_commit's weight is 4× llm_inference's: `(1×0.55 + 4×0.7)/5 = 0.67`, exactly matching step 2's output) — the confidence progression is not just passing assertions, it's arithmetically the behavior the hierarchy weighting is supposed to produce, and qualitatively matches "a test just confirmed this, it should be near-certain now."

## #5 — M5: Reasoning-Guided Traversal (spec.md §10-§11)

*MERGED*

## What

Implements M5 from `ROADMAP.md`: `packages/traversal`, seed nodes + task -> expanded subgraph, per spec.md §10-§11.

- **Batching (§10):** exactly one `reasoner.decide()` call per depth level over the whole ranked frontier — never one call per edge. The BFS-style loop in `traverse.ts` tracks `frontier` as only the nodes newly added at the previous level, so each iteration fetches neighbors of just the new boundary, not the whole visited set.
- **Ranking (§11):** `ranking.ts` implements `score = semantic_relevance + relation_importance + node_importance + confidence*weight + task_relevance + freshness - traversal_cost`. `confidence*weight` is a product per §3.3, not two additive terms (tested explicitly — see below). `relation_importance`/`node_importance` are lookup tables (§11 names the terms but doesn't give a table, so these are this PR's own reasonable ordering, e.g. `must_follow` > `references`, `invariant` > `variable`). `semantic_relevance` is embedding-cosine-similarity when a `taskEmbedding` is supplied (optional, like M2's embedder); `task_relevance` is a dependency-free lexical token-overlap signal so there's always *some* task-relevance term even with no embedder wired in.
- **Frontier fetch (§16):** one CTE query per depth level. Added `getFrontierEdges` to `packages/graph-store/src/edges.ts` (one `WITH frontier AS (...)` query per call, returning each edge plus which endpoint is the "new" neighbor) and `getNodesByIds` to `nodes.ts` for batch neighbor hydration — both used by `frontier.ts`'s `createPostgresGraphProvider`.
- **Budget (§10.1):** every `TraversalBudget` field is enforced — `maxDepth`, `maxNodes`, `maxEdges`, `maxReasoningSteps`, and `maxTokens` (via a rough chars/4 estimate on the content each expansion actually adds; the seed set's own token cost is out of scope here, that's retrieval's/M2's concern).
- **Injected interfaces:** `GraphProvider` and `ReasoningProvider` are both injected (same pattern as M2's `EmbeddingProvider`), so `traverse.ts`'s loop is fully unit-testable against an in-memory fixture graph and a scripted reasoner, with the real Postgres path covered separately by an integration suite.

## How it was verified

**Unit tests** (`packages/traversal/src/ranking.test.ts`, `traverse.test.ts`) — always run, no DB required:
- confidence*weight is a product, not a sum (two edges with the same product but swapped confidence/weight score identically; a higher-product edge outscores both)
- relation/node importance ordering (`must_follow`/`invariant` outranks `references`)
- lexical task-relevance and freshness terms move the score in the right direction
- semantic_relevance only contributes when both a `taskEmbedding` and a node embedding are present
- **budget-exhaustion**: a 100-neighbor star graph with `maxNodes: 5` still terminates with exactly the budgeted node count and `stopReason: "budget_exhausted"`
- **maxDepth**: a 10-hop chain with `maxDepth: 3` stops at depth 3 even though every level has more to expand
- **maxTokens**: a star graph with long node summaries and generous `maxNodes`/`maxEdges` but a tight `maxTokens` still terminates early on token cost alone
- **call-count / batching proof**: a 4-hop chain where each node also has 2 dead-end "junk" edges — `reasoner.callCount === depthReached` (4) and strictly less than total edges encountered (12), proving one call per depth level, not per edge
- reasoner `stop: true` halts immediately without expanding further
- an empty-edge seed returns `stopReason: "no_frontier"` immediately

**Integration tests** (`integration.test.ts`, gated on `DATABASE_URL`, run against real Postgres in this session):
- `createPostgresGraphProvider` end-to-end through real `getFrontierEdges`/`getNodesByIds` queries, expanding from a seed through both a high-weight and a low-weight edge
- a 2-cycle (`a -> b -> a`) never re-offers an already-visited node as a "new" candidate — confirms the exclude-neighbor-ids CTE filter and the traversal loop's own dedup both hold

Full workspace suite (`pnpm -r build && pnpm -r typecheck && pnpm lint && pnpm test`, `DATABASE_URL` set) is green — 97 tests total across all packages, no regressions.

**Self-review:** ran the `code-review` skill against the diff. It found two real issues, both fixed and re-verified:
1. `maxTokens` wasn't enforced anywhere despite being part of `TraversalBudget` — added the token-estimate accounting described above, plus a dedicated unit test.
2. When every neighbor of a frontier had been filtered out (e.g. all soft-deleted since the edge was last written), the loop reported `stopReason: "low_relevance"` (misleading — no scoring ever happened) and didn't decrement `depth`, inconsistent with the identical `rawFrontier.length === 0` case a few lines above. Fixed to treat "zero viable candidates after hydration" the same as "zero raw frontier edges."

**Manual sanity check:** built a small realistic subgraph outside the test fixtures (`PaymentService` calling `PaymentRepository`/`validatePaymentAmount`, constrained by a `PaymentRetryIdempotencyInvariant`, plus an unrelated `DateFormatter` utility) against real Postgres, and ran `traverse()` with a threshold-based reasoner (not either test double — a policy that expands anything within 0.3 of the frontier's top score) for the task *"why does PaymentService retry failed charges without double-charging."* Read the actual output: the reasoner correctly favored the retry invariant over the unrelated `DateFormatter` (which was never touched at either depth), and reached `PaymentRepository` one hop later via the invariant's own back-edge rather than the direct `calls` edge — a legitimate outcome of the ranking formula (the invariant edge's `constrained_by` relation-importance plus its stronger task-relevance match narrowly outscored the direct call at depth 1), not a bug. This is exactly the kind of "technically-passes-but-check-the-behavior" scenario the sanity check step exists to catch, and the behavior held up.

## Deviations from spec.md

None. §11's ranking terms (`relation_importance`, `node_importance`, `semantic_relevance`, `task_relevance`) aren't given concrete tables/formulas in the spec, only named — the lookup tables and lexical/embedding-based computations in `ranking.ts` are this PR's own reasonable implementation choice, not a deviation from anything spec.md actually decided.

## #6 — M6: Context Construction (spec.md §17)

*MERGED*

## Summary

Implements M6 — Context Construction per spec.md §17 and ROADMAP.md's acceptance criteria: subgraph → compact, task-specific projection (relevant subsystem, relationships, invariants, prior experience, source files), via plain templating over the subgraph — no new LLM call.

New package `packages/context`:
- **`types.ts`** — `Subgraph` (nodes/edges + already-fetched `experiences`) as the input, `AgentContext` as the five-section output structure.
- **`build.ts`** — `buildContext(subgraph, task, options?)`: pure, synchronous templating. Groups nodes by `NodeType` into subsystems/invariants/source files, resolves relationship endpoint names from the node set, orders relationships by weight (spec.md §3.3) and experiences by recency, and caps every section for compactness.
- **`render.ts`** — `renderContext(context)`: turns the structured `AgentContext` into the Markdown text an agent actually reads.
- **`hydrate.ts`** — `hydrateExperiences(nodeIds)`: the one piece of I/O in this package — fetches prior experience touching any of the given nodes via `packages/episodic`'s `queryByNode`, deduped by experience id. Kept separate from `buildContext` so the templating logic itself stays DB-free and trivially unit-testable (same DI-flavored separation M5's `GraphProvider`/`ReasoningProvider` and M2's `EmbeddingProvider` use, just simpler since no injected interface is needed — the caller just assembles the `Subgraph` before calling `buildContext`).

- **Integration test** (`integration.test.ts`, gated on `DATABASE_URL`): `hydrateExperiences` against real Postgres, confirming dedup when one experience's `relatedNodes` touches more than one queried node.
- Ran `pnpm --filter @cognitive-memory/context test` (9/9 pass, integration test executed for real, not skipped) and `pnpm -r build && pnpm -r test && pnpm -r typecheck && pnpm lint` across the whole monorepo — all green.

## #14 — Self-improve: batch incremental-deletion transactions instead of one per node

*MERGED*

## What changed

`extractChangedFiles` in `packages/structural/src/incremental.ts` (M1) and
its parallel copy in `packages/structural-python/src/incremental.ts` (M8)
opened one Postgres connection checkout + one `BEGIN`/`COMMIT` transaction
**per deleted node**, instead of batching a single incremental call's
deletions into one transaction. This surfaced while self-reviewing the M8
PR (#13) — the pattern was copied verbatim into the new Python package, and
flagged at the time as pre-existing rather than fixed in that PR (mixing an
M1 fix into an M8 PR would have crossed milestone boundaries). This cycle
fixes it in both places.

Two real problems with the old pattern:
- **Atomicity**: deleting 3 nodes from one changed file did 3 *separate*
  transactions. A crash between the 1st and 2nd would leave the graph
  partially desynced from the event log (spec.md §14) — exactly the
  failure mode transactions exist to prevent, just not applied at the right
  granularity.
- **Overhead**: N connection checkouts + N transaction round-trips instead
  of 1, for what is logically one atomic operation (one incremental update
  call).

The fix: collect every node to delete across all of `changedFilePaths`
first, then run the whole delete/event/stale-edge sequence inside a single
transaction on one checked-out connection.

## Measured (real Postgres, `cognitive_memory_test`)

Added a test to both packages' `integration.test.ts` that spies on
`getPool().connect()` around an `extractChangedFiles` call deleting 3
functions from one file in a single incremental update, and asserts the
call count — reproducible by anyone with `DATABASE_URL` set by running
`pnpm --filter @cognitive-memory/structural test` /
`pnpm --filter @cognitive-memory/structural-python test`.

- **Before** (`packages/structural`): wrote the test against the unfixed
  code first — **5** `connect()` calls for 3 deleted nodes (1 from
  `getNodesByPath`'s `pool.query()`, which node-postgres's `Pool.query`
  checks out a connection for internally, + 3 from the per-node deletion
  loop + 1 from `persistExtraction`'s own transaction).
- **After**: **3** `connect()` calls — same 1 (`getNodesByPath`) + 1
  (batched deletion transaction) + 1 (`persistExtraction`) — constant
  regardless of how many nodes get deleted in one call, instead of scaling
  with deleted-node count.
- Same test/fix applied to `packages/structural-python`, same before/after
  shape (verified independently against its own unfixed code before
  applying the fix there too).

The two that are decisions, now in spec.md §25.8:

1. **A harness must declare its database.** §25.1 counted "no environment

   they cannot retract do not get it.
2. **The transaction queue serializes transactions, not writes.** One connection
   means an untransacted `getDb().query(...)` during an open transaction lands
   *inside* it and rolls back with it, where Postgres committed it independently
   on another pooled connection. Nothing here writes that way, so this is
   documented and pinned by a test rather than architected around. The
   neighbouring defect was real, though: `withTransaction` resolved `getDb()` when
   the **queue** reached it, so a transaction enqueued across a `closeDb()`

   writes into the live memory file. It now captures the handle at call time and
   fails on a closed connection instead.

variable, or without a `claude` binary, sync degrades to raw bodies per memory
rather than failing.
